# 前置 VTOYEFI 无损安装

## 设计边界

用户先用分区软件在磁盘前部留出未分配空间。本功能只在这块空间写入 Ventoy，保持原数据分区的起点、大小和文件系统内容；不负责移动或缩小原数据分区。原数据分区由第 1 项移为第 2 项，其他表项只在插入所需范围内后移。GPT 原有分区 GUID 保留，分区编号可能变化。

仅接受 512 字节逻辑扇区的基本 MBR/GPT 磁盘（包括 512e，不包括 4Kn）。GPT 限定 128 个 128 字节表项、主表在 LBA 2、备份表在磁盘末尾，要求主备表有效且一致，已使用表项的 GUID 非零且不重复。拒绝扩展/逻辑分区、LDM、Storage Spaces、重叠分区和没有空分区表项的布局。Windows 保留系统盘禁止安装，并通过物理磁盘编号、分区起点和长度匹配实际数据卷；可识别的无盘符卷也可通过检查。

Windows 前置安装和升级要求实际数据卷为可读的 NTFS、exFAT、FAT 或 FAT32，并核对原始文件系统签名。此 Windows 路径不支持 ReFS、UDF 或无法识别的文件系统，不能以同盘其他分区可读代替实际数据卷检查。BitLocker 等加密卷即使已在 Windows 中解锁，也不能据此认定 Ventoy 启动时可读。

固定布局（LBA 以 512 字节为单位）：

| 范围 | 用途 |
| --- | --- |
| LBA 0–2047 | 分区元数据及 BIOS 引导区域 |
| LBA 2048–67583 | 第 1 分区 VTOYEFI，32 MiB |
| LBA 67584 至原数据分区起点 | 保持未分配；允许有间隙 |
| 原数据分区的原位置 | 第 2 分区，起点至少 67584，即 33 MiB |

建议用户预留 64 MiB，程序只使用前 33 MiB，其余间隙不处理。文件系统内的可用空间不等同于分区前的未分配空间。手工移动原分区本身的风险不由本功能消除。

新布局保留现有 EFI 镜像大小及 GPT 类型/属性策略。旧标准布局继续使用原安装、升级入口。前置布局按数据/EFI 角色定位，数据实际起点通过现有启动参数和 sysfs 取得，不固定成 33 MiB。

## 使用入口

以下命令仅用于已完整重建、包含有效 `ventoy/front-efi.sha256` 的安装包。仓库现有预编译文件不代表已经支持本改动。

Windows 图形界面：配置选项 → 无损安装（EFI 前置）。

确认窗口显示目标物理磁盘、型号、容量、盘符、分区类型、实际数据卷及文件系统和数据分区起点，并默认选择取消。操作期间禁用刷新、设备切换和菜单；后台使用独立磁盘信息副本。空间不足时直接显示首个分区起点和所需空间，其他预检失败分别提示具体原因及处理方法。

Windows CLI（将 N 替换为核实后的物理磁盘编号）：

```text
Ventoy2Disk.exe VTOYCLI /I /FrontEfi /NoSB /PhyDrive:N
Ventoy2Disk.exe VTOYCLI /U /NoSB /PhyDrive:N
```

`/FrontEfi` 隐含无损安装，仅可用于 `/I`。升级自动识别前置布局。安装器与备份必须位于另一块物理磁盘。前置路径不启用 Secure Boot，启动时须关闭固件 Secure Boot。

Windows CLI 拒绝未知或拼错的参数、重复/冲突操作、多个目标和无效磁盘编号；`/FrontEfi` 与 `/GPT`、`/R:`、`/FS:` 不能合用。拼错前置选项不会转入普通格式化安装。命令行仍用于无人值守调用，不增加交互确认；执行前需核对目标编号。

CLI 在启动文件检查前清理旧完成标记；清理失败会停止。缺少安装文件时记录失败并返回非零退出码，避免弹出无人处理的图形对话框。图形界面的语言 JSON 按字段名读取并验证关键提示；不可用时尝试 INI，仍无有效语言则停止启动，避免使用空白警告继续安装。

Linux CLI（将 sdX 替换为核实后的整盘设备）：

```sh
sudo sh Ventoy2Disk.sh -i --front-efi /dev/sdX
sudo sh Ventoy2Disk.sh -u /dev/sdX
```

`--front-efi` 不与 `-n`、`-r`、`-g` 或 `-L` 合用，保留原磁盘分区类型；已有 Ventoy 不重复执行无损安装。操作和目标只能指定一次，重复/冲突选项、缺少 `-L`/`-r` 的值、将安装专用选项用于升级或列表均会停止。数据分区写入前须卸载，不能用作活动 swap、RAID 或设备映射器成员。安装包及工作目录应放在其他磁盘。

Linux 前置安装和升级均在确认前显示目标型号、容量、分区起点及恢复目录；取消或输入结束时保留原挂载状态。确认且镜像准备完成后，按真实设备号和 sysfs 子分区精确卸载，支持设备别名、FUSE 卷及含空格的挂载路径，避免误匹配名称前缀相同的其他磁盘；被其他设备覆盖的挂载点、卸载失败或自动重新挂载会使操作停止。需准备约 66 MiB 的内存和工作空间，工作盘建议至少留出 80 MiB；空间和内存不足会在首次写盘前停止。临时挂载点卸载失败时停止，只允许删除已卸载的空目录，不递归清理其中内容。

精确卸载依赖宿主 Linux 的 `stat`、`readlink`、`mountpoint`；缺少工具时明确提示并停止。项目自带精简 `ash` 不包含这些工具，精简发行版及 BusyBox 环境的参数兼容性尚未实测。

LinuxGUI 可以识别新布局，但前置布局升级明确转交 CLI，防止进入旧 GUI 写入流程。Plugson 按实际数据分区定位配置文件。

## 写入及恢复

安装前核对前部空闲区、分区表、扇区大小和安装包 SHA256。先保存备份并完整准备启动镜像，再写 EFI 内容、引导内容，最后提交新分区表；写入后回读比对。GPT 同时维护主备分区表与 CRC。升级保留磁盘 UUID 和 LBA 2040–2047 的配置区域，该配置区域也随引导内容回读验证。Windows 对启动文件短读、解压失败、长度不符和 EFI 文件替换失败立即停止，不将损坏的内存镜像当成有效源写盘。

Windows 将备份保留为安装目录下 `ventoy/front-efi-diskN-PID-TICK.bin`：

- 前 33 MiB 原始内容；
- GPT 额外拼接磁盘最后 33 个扇区；MBR 无此尾部。

Windows 同时生成同名 `.bin.txt` 恢复信息文件，记录磁盘身份、容量、扇区大小、备份区域和备份 SHA256；备份及信息文件完整写入、刷新且回读比对成功后才写盘。恢复时必须同时保留两者并核对身份与哈希，不能仅凭拔插后可能变化的物理磁盘编号选择目标。此信息文件在写盘前生成，不代表后续安装或回滚已成功。

Windows 核对备份目录实际所在物理磁盘和可用空间，界面及日志显示完整备份路径（可能采用卷 GUID 路径）。每次写入前登记可能改动的范围，包括失败请求中无法排除已写入的部分。同次调用中只有明确不属于介质故障的错误才尝试恢复这些范围；不再无条件回写整个前 33 MiB。恢复范围全部回读比对通过才报告“已恢复”；备份始终保留。结果明确区分“尚未写盘”“已恢复且验证通过”“已写入、恢复未确认”。写入受阻时不进入删除 EFI 分区、修改分区类型或清盘重试。

Linux 在当前安装目录创建 `ventoy-front-backup.*`，包含 `snapshot.bin`、`disk.txt`、`front-33MiB.bin`、`tail-33sectors.bin` 和准备好的启动镜像。备份文件先写入、同步并回读比对，再生成并同步 `backup.ready`。该标记只表示备份准备完成，不表示后续安装成功；失败后保留文件，不自动回滚。

Linux 的尾部备份只对 GPT 读取末尾 33 个扇区；MBR 对应文件为空，`disk.txt` 中 `tail_bytes=0`，不读取与本次操作无关的磁盘尾部。若完成标记自身保存失败，只清理本次创建的失败标记；清理或同步失败时明确提示标记不可信，目标磁盘尚未写入。

Linux 写入集中在 `vtoycli partresize -W`：一次以 `O_EXCL` 打开磁盘，核对确认前快照，完成备份并再次核对后才写入；使用同一磁盘句柄完成写入和回读。回读使用内存缓冲区，首次写盘后不再创建大临时文件。内部返回值 `1` 表示未写盘，`3` 表示已尝试写入、需检查恢复；异常中断提示磁盘可能已写。`disk.txt` 记录容量、设备号、可用的内核 diskseq 以及备份 CRC32。旧内核没有 diskseq 时，仍核对设备号、容量和完整分区快照，但无法仅据此区分使用相同设备号且内容完全相同的克隆磁盘。

安装、升级期间都应关闭其他分区工具，避免并发修改。Windows 锁定磁盘句柄后核对设备属性及完整分区表；Linux 在首次写盘前再次核对身份和分区快照。

断电情况下不保证自动恢复。恢复前必须核对原磁盘、容量和备份来源，不能通过重新执行普通格式化安装代替恢复。

## 坏块、掉线和读写故障

读写错误不能单凭错误码直接认定为坏块。前置路径记录失败阶段、读/写/刷新/校验操作、目标磁盘或备份文件、请求字节范围及磁盘 LBA 范围、实际传输量和系统错误码。记录的范围是失败请求涉及的范围，不代表已经精确定位每一个坏扇区；刷新失败尤其不能定位为某一个扇区。回读内容不一致与系统 I/O 错误分别报告。Windows 保留原始故障和回滚故障两份诊断，避免恢复操作覆盖最初原因。

- 首次写盘前读取或备份失败：停止，保持目标磁盘未写入。备份文件未验证时不能作为完整恢复依据；备份盘异常应换健康的备份位置。
- EFI、引导区写入或回读失败：停止后续提交。Windows 以 1 MiB 为单位写入并刷新、回读 EFI 内容，发现故障后不继续写后面的块。
- 疑似介质故障、设备掉线、超时、短传输或回读不一致：Windows 停止自动追加写入和回滚；未知磁盘 I/O 故障也保守停止。Linux 的真实 I/O 错误立即终止，仅对 `EINTR` 重新调用，并按成功返回的实际传输量继续完成请求；零进展按失败处理，不跳过坏扇区。
- GPT 提交：两端均先写入、刷新并回读验证备份表及备份头，再提交主表并验证。中途失败仍可能留下主备表不一致，不能视为安装成功。

本功能不执行坏块修复、全盘读写扫描或“忽略错误继续安装”。已有前部备份读取只覆盖本功能涉及的区域，成功不代表整盘健康，也不能保证接下来的写入一定成功。操作系统或设备固件内部的 I/O 超时可能较长，本功能不承诺固定秒数内退出。

回读采用现有文件及设备句柄；刷新后比对能够发现返回错误或内容不一致，但不等于绕过操作系统、控制器及磁盘全部缓存的介质检测。

持续发生读写故障时，应先将可读数据抢救到健康磁盘，保留备份、错误记录和恢复进度，再在副本上处理文件系统或恢复分区。不要直接在故障原盘上反复安装或修复文件系统。该原则与 [GNU ddrescue 的安全建议](https://www.gnu.org/software/ddrescue/manual/ddrescue_manual.html#Important-advice) 一致。

## 构建与防止混用旧产物

前置安装及升级要求安装包根目录下的 `ventoy/front-efi.sha256` 严格列出以下三个文件：

1. `boot/boot.img`
2. `boot/core.img.xz`
3. `ventoy/ventoy.disk.img.xz`

清单由完整打包流程生成。不要手工生成清单以跳过构建校验；只修改安装器 EXE 或 Shell 脚本无法得到可启动的新布局。

在项目原有 Linux 构建环境中，从 INSTALL 目录运行：

```sh
sh all_in_one.sh FRONT_EFI
```

打包校验 GRUB 构建回执及关键组件中的 `VTOY_FRONT_EFI_V1` 能力标记，缺失则拒绝前置包。Windows 安装器和四架构 `vtoycli` 还必须包含本轮介质故障处理的 `VTOY_FRONT_EFI_SAFE_V3` 标记；Linux 脚本运行前查询工具协议版本，拒绝旧 helper 与新脚本混用，避免旧工具缺少备份回读和故障诊断仍继续写盘。普通包可保留旧组件，但不生成前置清单。GRUB 回执绑定实际 BIOS/EFI 启动二进制；BIOS core 内部压缩，不能只在压缩文件中搜索字符串判断版本。

必须重建受影响的 Windows 安装器、PE `vtoyjump`、GRUB、Ventoy EFI、VtoyTool、vtoycli、LinuxGUI/Plugson，并重新打包 cpio 和 EFI 分区镜像。原签名流程保留；本次不提供已受信任的 Secure Boot 签名。

VtoyTool `01/02` 为旧兼容工具链的产物，仓库没有提供对应构建说明，须在相应环境重建。不能把 `00` 复制过去冒充兼容版本。各 Unix 平台的预编译模块也不能因源码修改而视为已验证。
